# Отчёт по багам — FemAction-BOT

Дата анализа: 2026-05-31
Проанализированы все файлы в `src/`, конфигурация Docker и документация.
Тип-чек (`tsc --noEmit`) проходит без ошибок — все баги ниже логические/поведенческие, а не на уровне компиляции.

Легенда серьёзности:
- 🔴 **Высокая** — ломает основную функциональность или поведение очевидно неверно.
- 🟠 **Средняя** — заметная проблема надёжности/UX или мина замедленного действия.
- 🟡 **Низкая** — мелочь, edge-case, чистота кода.

## 🔴 Высокая серьёзность

### 1. Кулдаун общий на весь сервер, а не на пользователя
**Файлы:** `src/lib/cooldowns.ts:20,51`, `src/events/messageCreate.ts:38,88`, `src/events/interactionCreate.ts:23,71`

`CooldownManager` хранит время по ключу `(guildId, commandName)` — измерения «пользователь» нет вообще:

```ts
check(guildId: string, commandName: string)
set(guildId: string, commandName: string)
```

Из-за этого **один человек, использовавший `/hug`, блокирует команду `hug` для ВСЕХ участников сервера на 20 секунд.** На активном сервере команды почти всегда будут «на кулдауне» из-за чужих вызовов. Для РП-бота кулдаун почти наверняка должен быть индивидуальным (на пользователя, обычно — на пользователя+команду).

**Фикс:** добавить в ключ `userId`. Например, хранить `Map<guildId, Map<\`${userId}:${commandName}\`, ts>>` или менять сигнатуру на `check(guildId, userId, commandName)` и передавать `message.author.id` / `interaction.user.id`.

### 2. Все ссылки на GIF — это заглушки и не загрузятся
**Файлы:** `src/actions/bite.ts`, `boop.ts`, `hug.ts`, `kiss.ts`, `pat.ts`, `silly.ts`

Во всех действиях указаны фиктивные URL вида:

```ts
gifs: [
  'https://media.tenor.com/example-bite-1.gif',
  'https://media.tenor.com/example-bite-2.gif',
],
```

Это не настоящие адреса Tenor (реальные выглядят как `https://media.tenor.com/<id>/<name>.gif`). В результате эмбед отправляется с битой картинкой — основная фишка бота (показ гифок) не работает «из коробки». Скорее всего это плейсхолдеры, которые забыли заменить, но в текущем виде бот выкатывается с неработающими гифками во всех командах.

**Фикс:** заменить на реальные URL гифок.

### 3. Цель действия не получает пинг, когда есть гифка (несогласованное поведение)
**Файлы:** `src/lib/buildResponse.ts:61-71`, `src/events/messageCreate.ts:80-84`, `src/events/interactionCreate.ts:63-67`

Когда у действия есть гифка, текст с упоминанием `<@id>` кладётся в **описание эмбеда**, а `content` остаётся пустым:

```ts
const embed = new EmbedBuilder()...setDescription(text).setImage(gif);
return { content: '', embed };
```

Discord **не отправляет уведомление по упоминаниям внутри эмбеда** — они отображаются как ссылка, но цель не пингуется. При этом `allowedMentions: { parse: ['users'] }` навешен на сообщение, но он влияет только на `content`, который здесь пуст, → для гиф-команд этот параметр мёртвый.

Получается несогласованность: без гифки (текст в `content`) цель пингуется, с гифкой — нет. Так как у всех действий гифки заданы, цель **никогда** не получает уведомление.

**Фикс:** если нужно уведомлять цель — дублировать упоминание в `content` (например, `content: targetMention ?? undefined`) либо осознанно отказаться от пинга и убрать вводящий в заблуждение `allowedMentions`.

## 🟠 Средняя серьёзность

### 4. Хардкод `'silly'` в 5 местах вместо проверки `customEmbed`
**Файлы:** `src/lib/deployCommands.ts:25`, `src/events/interactionCreate.ts:38,41`, `src/events/messageCreate.ts:52,59`, `src/commands/help.ts:18`

Специальная обработка действия с кастомным эмбедом размазана по коду через сравнение строки:

```ts
if (action.name !== 'silly') { builder.addUserOption(...) }   // deployCommands
const target = action.name === 'silly' ? null : ...;          // оба обработчика
if (a.name === 'silly') { ... }                               // help
```

В типах для этого специально есть поле `customEmbed` и комментарий «работает только на себя», но обработчики проверяют не его, а захардкоженное имя. Любое новое кастомное действие (или переименование `silly`) придётся вручную править в 5 местах, иначе у него появится лишняя опция цели и сломается логика. Это потенциальный источник будущих багов.

**Фикс:** ввести флаг в `ActionDefinition` (напр. `noTarget?: boolean` / `selfOnly?: boolean`) или проверять `Boolean(action.customEmbed)`, и заменить все сравнения `=== 'silly'` на него.

### 5. Нет обработки ошибок в обработчиках событий
**Файлы:** `src/events/messageCreate.ts:12`, `src/events/interactionCreate.ts:8`

Колбэки `client.on(...)` асинхронные и не обёрнуты в `try/catch`. Любое исключение (например, `message.reply` по удалённому сообщению, `Unknown interaction`, сетевой сбой при `interaction.reply`) превращается в необработанный промис-реджект. Для слеш-команды это означает зависшее «Эта команда не сработала» у пользователя без какой-либо обработки/логирования.

**Фикс:** обернуть тело каждого обработчика в `try/catch`, логировать ошибку и (для интеракций) при возможности отвечать пользователю ephemeral-сообщением об ошибке.

### 6. Dockerfile: падение регистрации команд блокирует запуск бота
**Файл:** `Dockerfile:30`

```dockerfile
CMD ["sh", "-c", "node dist/lib/deployCommands.js && node dist/index.js"]
```

`deployCommands` при ошибке регистрации выставляет `process.exitCode = 1` (`src/lib/deployCommands.ts:64`), из-за чего процесс завершается с ненулевым кодом. Из-за `&&` бот (`index.js`) тогда **не запустится вовсе**. В связке с `restart: unless-stopped` в `docker-compose.yml` транзиентная ошибка Discord API при старте → контейнер уходит в краш-луп и бот не поднимается. Кроме того, перерегистрация команд на каждом старте контейнера — лишний расход лимитов Discord.

**Фикс:** разделить деплой команд и запуск (например, отдельный one-shot шаг/сервис), либо использовать `;` вместо `&&`, либо не падать в `deployCommands` при ошибке регистрации.

### 7. `ephemeral: true` устарел в discord.js 14.26.4
**Файлы:** `src/events/interactionCreate.ts:32,49`, `src/commands/help.ts:54`

В установленной версии (14.26.4) поле помечено `@deprecated`:

```ts
/** @deprecated Use {@link InteractionReplyOptions.flags} instead. */
ephemeral?: boolean;
```

Сейчас работает, но генерирует депрекейшн-предупреждения и будет удалено в v15.

**Фикс:** использовать `flags: MessageFlags.Ephemeral` (импорт `MessageFlags` из `discord.js`).

## 🟡 Низкая серьёзность / чистота

### 8. Гонка в кулдауне (check-then-set через `await`)
**Файлы:** `src/events/messageCreate.ts:38→88`, `src/events/interactionCreate.ts:23→71`

Кулдаун проверяется в начале, а устанавливается только **после** `await ...send/reply`. Два почти одновременных вызова успевают оба пройти проверку до того, как любой из них вызовет `set()`, и кулдаун обходится. Усугубляется глобальностью кулдауна (баг №1).

**Фикс:** ставить кулдаун сразу после успешной проверки (до отправки), а не после отправки.

### 9. `message.mentions.users.first()` ненадёжно выбирает цель
**Файл:** `src/events/messageCreate.ts:52`

`.users` формируется в порядке API, а не по порядку в тексте (см. discord.js `MessageMentions`), и **включает пользователя, на чьё сообщение отвечают** (reply с пингом). Поэтому `!обнять` в ответ на чужое сообщение может «обнять» автора того сообщения, а при нескольких упоминаниях цель может оказаться не той, что ожидал пользователь.

**Фикс:** парсить первое упоминание из текста аргументов вручную или явно исключать `message.mentions.repliedUser`.

### 10. README ссылается на несуществующий сервис `FemAction-BOT`
**Файлы:** `README.md` (команды `docker compose run --rm FemAction-BOT ...`), `docker-compose.yml:2`

Сервис в compose называется `femaction-bot` (нижний регистр), а в README — `FemAction-BOT`. Имена сервисов чувствительны к регистру, поэтому документированная команда упадёт с `no such service: FemAction-BOT`. Вдобавок этот шаг частично избыточен — деплой команд уже выполняется в `CMD` контейнера.

**Фикс:** привести имя в README к `femaction-bot`.

### 11. `CooldownManager.cleanup()` никогда не вызывается
**Файл:** `src/lib/cooldowns.ts:65`

Метод очистки устаревших записей определён, но нигде не запускается (нет ни `setInterval`, ни вызова). Записи по командам, которые перестали использоваться, не вычищаются (чистка происходит только лениво при `check()` той же команды). Утечка небольшая, но метод сейчас — мёртвый код.

**Фикс:** либо периодически вызывать `cleanup()` (`setInterval`), либо удалить метод.

### 12. Неиспользуемые поля в результате `check()`
**Файл:** `src/lib/cooldowns.ts:41-45`

`check()` возвращает `{ seconds, ms, timestamp }`, но потребители используют только `seconds`. Поля `ms` и `timestamp` — остатки от отката динамического таймстампа (см. git-историю: «show cooldown remaining as static text»). Мёртвый код.

**Фикс:** убрать неиспользуемые поля.

### 13. Несогласованные пороги и дубликат gif в `silly`
**Файл:** `src/actions/silly.ts`

Границы диапазонов для текста, цвета и гифки не совпадают. Например, при `value = 55`: текст — «Средний уровень глупости» (порог `<= 60`), но цвет — оранжевый (`<= 75`), а гифка — из набора «silly» (`<= 75`). Сообщение говорит «средний», оформление — «глуповатый». Также URL `example-silly-12.gif` дублируется в двух наборах (`averageGifs` и `sillyGifs`).

**Фикс:** согласовать пороги текста/цвета/гифки по единым диапазонам.

### 14. Мёртвая ветка `requireTarget`
**Файл:** `src/events/messageCreate.ts:53`

Ни одно действие не задаёт `requireTarget: true`, поэтому ветка с подсказкой «Укажи цель …» недостижима. Не баг, но мёртвый путь — стоит либо задействовать, либо помнить при ревью.

### 15. Избыточное условие `&& action.name !== 'silly'`
**Файлы:** `src/events/interactionCreate.ts:41`, `src/events/messageCreate.ts:59`

В проверке «нельзя выбрать себя» для `silly` `target` уже принудительно `null` (строки 38/52), поэтому добавочное `&& action.name !== 'silly'` всегда истинно и избыточно.

### Что и как исправлено

- **#4** — в `ActionDefinition` добавлен флаг `noTarget`, у `silly` выставлен `noTarget: true`. Все сравнения `action.name === 'silly'` в `deployCommands.ts`, обоих обработчиках и `help.ts` заменены на проверку `noTarget`.
- **#5** — тела обработчиков `messageCreate`/`interactionCreate` обёрнуты в `try/catch` с логированием; для слеш-команд при ошибке отправляется ephemeral-сообщение, если ещё не ответили.
- **#7** — `ephemeral: true` → `flags: MessageFlags.Ephemeral` в `interactionCreate.ts` и `help.ts`.
- **#8** — кулдаун теперь резервируется (`set`) синхронно перед `await ...send/reply`, после прохождения валидаций → гонка закрыта.
- **#9** — при выборе цели исключается `message.mentions.repliedUser` (reply-пинг больше не становится целью).
- **#10** — в `index.ts` добавлен `setInterval(() => cooldowns.cleanup(), 5 мин).unref()`.
- **#11/#12** — `check()` теперь возвращает `{ seconds }`; неиспользуемые `ms`/`timestamp` и их вычисление убраны.
- **#13** — логика `silly` переписана на единую таблицу тиров (фраза/цвет/гифка из одного тира → всегда согласованы), дубликат `example-silly-12.gif` устранён.
- **#15** — убрано избыточное `&& action.name !== 'silly'` (для `noTarget`-действий `target` уже `null`).

**#14** оставлено намеренно: `requireTarget` — рабочая, задокументированная в `types.ts` возможность; ни одно текущее действие её не включает, но удаление убрало бы функциональность. Если нужно — скажи, уберу.

После всех правок `tsc --noEmit` и `npm run build` проходят без ошибок.

**Не тронуто по решению автора:** №1 (кулдаун на сервер), №2 (плейсхолдер-гифки), №3 (пинг цели в эмбеде), №6 (Dockerfile `deploy && start`).
